## 2. 后续开发总原则

1. 不推倒重写，沿用现有 `miniprogram / cloudfunctions / docs / tests` 模块化结构。
2. 每阶段必须新增对应 `docs/dev-records/XX_xxx.md` 并更新本 `index.md`。
3. 每阶段必须补充测试文件或更新既有测试，保证 `npm test` 全部通过。
4. 当前产品策略明确只使用 mock 支付，不考虑接入真实支付现金流；真实微信支付、真实退款、真实提现、分账能力仅作为后续条件阶段保留，不作为当前工程 P0 阻塞项。
5. 资金、分佣、提现、合伙人、PC后台属于高权重高风险模块，必须拆阶段开发。
6. 所有资金相关动作必须有流水、日志、幂等校验、权限校验和回冲机制。
7. 所有平台规则必须优先配置化，不要硬编码到页面。
8. 业务核心流程优先级高于 UI 美化和 AI 增强。
9. GitHub raw 抓取或网页渲染显示源码为单行，不得直接作为工程问题；只有通过 zip、本地源码、微信开发者工具或可靠文件内容确认后，才能将格式异常列为问题。
10. 阶段 22C 开始后，用户端页面的状态文案和状态 tone 应逐步迁移到 `getStatusView(type, status)`，并优先通过 `status-tag` 展示；本规则只约束展示字段组装，不改变状态枚举、数据结构或业务流程。
11. 阶段 24E 后的开发顺序建议遵循：试运营云端验证 → 管理员营销配置 UI → 商家体验增强 → 规则派单与抢单策略 → 售后仲裁与附件上传 → 附近服务方发现 → PC后台 → 运营配置与数据看板 → 合伙人与模拟分佣 → 安全合规与非真实支付版本验收。真实支付、真实认证、提现结算和 AI 能力均作为条件或暂缓阶段保留。

### 阶段 16：财务流水与服务方收益基础版

目标：建立基础账务结构，让订单从“服务闭环”升级为“交易闭环”。

核心功能：

- 新增 `finance_logs` 财务流水集合。
- 新增 `worker_earnings` 服务方收益集合。
- 订单完成后生成服务方收益记录。
- 支持平台固定抽佣比例，先 mock 配置。
- 支持收益状态：冻结中、可结算、已结算、已回冲。
- 售后退款后自动回冲未结算收益。
- 师傅端展示收益明细、冻结金额、可结算金额。
- 管理端展示订单财务流水。

关键要求：

- 不做真实提现。
- 不做合伙人分佣。
- 不做自动打款。
- 所有金额以后端订单金额为准。
- 财务流水必须幂等，不能重复生成。

### 阶段 17：会员与优惠券基础版

目标：补齐用户端基础营销能力。

核心功能：

- 新增 `memberships`、`coupons`、`user_coupons`、`coupon_usage_logs`。
- 会员档位：月卡29、季卡79、年卡199，后台可配置。

- 管理员创建优惠券、上下架优惠券。
- 用户领取优惠券。
- 下单时选择优惠券。
- 订单保存优惠前金额、优惠金额、实付金额。
- 退款时基于实付金额处理。
- 用户端展示会员权益与购买记录。

关键要求：

- 优惠金额不能由前端决定。
- 优惠券核销要幂等。
- 已用优惠券不可重复使用。
- 暂不做复杂活动与自动续费。

### 阶段 18：评价、追评、打赏与差评申诉增强

目标：补齐 PRD 中评价评分与用户打赏系统。

核心功能：

- 评价维度从单一评分升级为：服务态度、专业度、上门时效、性价比。
- 支持图文评价。
- 支持 30 天内追评。
- 7 天未评价自动默认好评，暂可先用手动任务/测试任务模拟。
- 服务商端支持差评申诉。
- 管理员审核差评申诉，可隐藏恶意评价。
- 用户可在评价后打赏。
- 打赏档位：6、12、18、28、58、自定义。
- 新增 `tips` / `tip_logs`，打赏默认 mock 支付。
- 打赏收益单独记录，预留服务方85%、平台15%的分配字段。

关键要求：

- 打赏不参与常规订单分佣。
- 打赏支付暂不做真实支付。
- 恶意评价处理必须有管理员日志。

  - 小区合伙人比例
  - 城市合伙人比例
  - 平台比例
