## 7. 数据库变化

本阶段开始实际使用 `users` 集合。代码中尚未自动创建集合，需在微信云开发控制台或微信开发者工具云开发面板中创建。

### 新增集合

- `users`

### users 字段说明

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | string | 用户记录 ID，由云数据库生成 |
| `openid` | string | 微信用户 openid |
| `nickname` | string | 用户昵称，默认 `社区用户` |
| `avatar` | string | 用户头像，第一版默认空字符串 |
| `phone` | string | 用户手机号，第一版默认空字符串 |
| `role` | string | 用户角色：user / worker / admin |
| `status` | string | 用户状态：normal / disabled |
| `created_at` | date | 创建时间 |
| `updated_at` | date | 更新时间 |

### 数据库权限说明

本阶段设计为通过云函数访问 `users` 集合。小程序页面不直接读写 `users` 集合。建议云数据库集合权限保持收紧，优先允许云函数读写，避免普通用户绕过云函数修改角色或状态。

### 管理员初始化方式

第一版管理员初始化采用手动方式：

1. 普通用户先在小程序“我的”页面点击登录
2. 云函数在 `users` 集合创建用户记录
3. 在云开发控制台找到该用户记录
4. 手动将 `role` 从 `user` 改为 `admin`
5. 用户重新登录或刷新“我的”页面后即可看到管理员入口

## 8. 云函数 / 接口变化

| 云函数 | 功能 | 入参 | 出参 | 权限要求 |
|---|---|---|---|---|
| `login` | 用户登录与初始化 | `action: loginOrRegister` | `{ user, isNewUser }` | 所有用户可调用 |
| `user` | 获取当前用户 | `action: getCurrentUser` | `{ user }` | 当前登录用户 |
| `user` | 更新当前用户资料 | `action: updateUserInfo`, `nickname/avatar/phone` | `{ user }` | 当前登录用户 |
| `user` | 管理员修改用户角色 | `action: updateUserRole`, `userId`, `role` | `{ user }` | 管理员 |
| `user` | 管理员禁用用户 | `action: disableUser`, `userId` | `{ user }` | 管理员 |

### 统一错误码

| 错误码 | 说明 |
|---|---|
| `OPENID_MISSING` | 无法获取 openid |
| `USER_NOT_FOUND` | 用户不存在 |
| `USER_DISABLED` | 用户已被禁用 |
| `PERMISSION_DENIED` | 当前操作无权限 |
| `USER_ID_MISSING` | 缺少用户 ID |
| `USER_ROLE_INVALID` | 用户角色不合法 |
| `ACTION_NOT_FOUND` | 未知 action |
| `INTERNAL_ERROR` | 未预期内部错误 |

## 9. 核心逻辑说明

### 登录逻辑

```text
用户点击“微信授权登录”
↓
前端优先调用 wx.getUserProfile 获取授权资料
↓
前端调用 loginService.loginOrRegister
↓
login 云函数通过 cloud.getWXContext 获取 openid
↓
查询 users 集合是否已有该 openid
↓
如果不存在，创建用户：
  nickname = 授权昵称或社区用户
  avatar = 授权头像或空字符串
  phone = ''
  role = user
  status = normal
↓
如果已存在且 status = normal，更新授权资料和 updated_at 并返回用户
↓
如果已存在且 status = disabled，返回 USER_DISABLED
↓
前端缓存 user 到本地 storage 和 app.globalData
↓
“我的”页面展示用户基础信息和角色入口
```

### 用户资料更新逻辑

```text
当前用户调用 user.updateUserInfo
↓
云函数根据 openid 查询当前用户
↓
如果用户不存在或已禁用，返回错误
↓
只允许更新 nickname / avatar / phone
↓
忽略 role / status 等敏感字段
↓
更新 updated_at
↓
返回更新后的用户信息
```

### 管理员修改角色逻辑

```text
管理员调用 user.updateUserRole
↓
云函数根据 openid 查询当前操作人
↓
校验当前操作人 role = admin
↓
校验目标用户存在
↓
校验目标 role 属于 user / worker / admin
↓
更新目标用户 role 和 updated_at
↓
返回目标用户信息
```

### 管理员禁用用户逻辑

```text
管理员调用 user.disableUser
↓
云函数校验当前操作人 role = admin
↓
查询目标用户
↓
将目标用户 status 设置为 disabled
↓
返回目标用户信息
```

## 10. 关键技术决策

### 决策 1：头像昵称第一版支持授权资料并保留默认兜底

原因：

- 当前目标需要先在微信开发者工具里看到授权登录交互
- 如果微信环境允许返回用户资料，可直接写入昵称和头像
- 先保证 openid、用户记录和角色体系稳定

影响：

- “我的”页面按钮文案为“微信授权登录”
- 如果授权资料可用，`users.nickname` 和 `users.avatar` 会写入授权值
- 如果授权资料不可用，仍使用 `社区用户` 和空头像作为兜底
- 后续可在用户资料编辑中补更完整的头像昵称维护方式

### 决策 2：手机号阶段二只保留字段

原因：

- 用户已确认手机号到下单或地址阶段再强制填写
- 阶段二重点是登录和角色，不提前扩大表单范围

影响：

- `users.phone` 默认空字符串
- “我的”页面展示手机号待填写
- 阶段四地址与下单时需要校验联系人手机号

### 决策 3：管理员初始化继续手动改库

原因：

- 用户已确认第一版采用手动改 `users.role`
- 不引入复杂管理员注册、邀请码或后台账号体系

影响：

- 阶段二记录手动操作步骤
- 阶段七可再考虑管理员初始化脚本或配置白名单

### 决策 4：云函数业务逻辑拆到 handler 中

原因：

- `index.js` 依赖 `wx-server-sdk`，不适合直接本地测试
- `handler.js` 可通过注入 openid、时间和仓储进行自动化测试
- 业务逻辑与云开发入口解耦，后续更易维护

影响：

- 每个云函数目录内保留 `index.js`、`handler.js`、`user-repository.js`
- 测试可以覆盖核心业务，不需要真实云环境
